# v3.3 升级要求与指南（池化模式 / Windows 节点）

本文以节点包 `SLC-Pool-Node-GUI-v3.3.zip`（你们内部 3.x 系列的“池化节点程序”）为例编写升级要求与操作步骤；若你实际要升级的是其他 3.x 版本（如 v3.21/v3.22…），步骤相同，仅替换对应安装包/版本号即可。

---

## 1. 升级目标（你们当前遇到的典型问题）

从服务器回传日志看，常见的“无法远程连接”不是卡在租赁授权，而是卡在被控端启动串流阶段：

- **后端已下发 `remoteSessionRequested`，但后端始终看不到 `type=offer`**：说明节点没有产出 WebRTC offer（通常是节点未进入 `startStreaming`、或在抓屏阶段崩溃/重启）。
- **GUI 节点日志停在**：`[v3.xx] 准备调用 desktopCapturer.getSources`，随后节点断线并重新拉 token/connection_info：高度怀疑 **崩在 `desktopCapturer.getSources` 的 native 内部**（Dart try/catch 来不及记录）。
- **节点断线重连后再点“远控”会提示 lease 无权限**：这是正常链路表现（lease 与当次节点连接/授权状态绑定），需要**重新租赁**再试。

本次升级指南会把“抓屏模式选择（默认抓屏 vs 虚拟显示器）”“Windows 服务会话/无显示器导致抓屏失败”作为重点要求写清楚。

## 2. 升级前置要求（必须满足）

### 2.1 Windows 节点运行形态要求

1) **优先要求：节点进程运行在交互桌面会话（非 Session 0）**
- 你们的服务包装器日志会出现类似：`Launching slc.exe in session 1`  
- 如果是 `session 0`（SYSTEM/服务会话），桌面抓取很容易失败或崩溃（抓不到交互桌面）。

2) **必须有可抓取的“屏幕源”**
- 物理显示器 / HDMI Dummy / 虚拟显示器驱动三选一。
- 若机器“无显示器”，默认抓屏可能出现 `getSources count=0` 或直接崩溃（依赖底层抓屏实现与显卡驱动）。

3) **管理员权限**
- 安装/重装 Windows 服务（`slcsvc`）需要管理员权限。

### 2.2 网络要求（最小集合）

- 节点到后端控制平面：能访问 `api_url`（HTTP）与 `/ws/`（WebSocket）。
- WebRTC：需要 UDP 出站（以及必要时 TURN 服务器可达）。若是严格 NAT/防火墙环境，请提前准备 TURN（coturn）。

### 2.3 配置要求：`C:\ProgramData\SLC\node.json`

节点启动时会读取该文件（由 `lib/control_plane/node_agent_config.dart` 解析）。建议字段：

- `enabled`: 是否启用 NodeAgent 模式（必须 `true`）
- `device_id` / `device_secret`: 设备身份（必须正确）
- `api_url`: 你们的后端控制平面地址（非常关键）
- `region` / `gpu_tier`: 资源池调度标签
- `heartbeat_seconds`: 心跳间隔（建议 10）
- `agent_version`: 节点版本标识（可用于后端展示/排查）
- `city`: 可选（展示用）
- `reboot_on_release` / `reboot_delay_seconds`: 释放后是否重启（按你们的池化策略）

示例（建议把 `api_url` 补齐）：

```json
{
  "enabled": true,
  "device_id": "hk-gpu-001",
  "device_secret": "REPLACE_ME",
  "region": "hk",
  "gpu_tier": "tier_7",
  "heartbeat_seconds": 10,
  "agent_version": "3.3.0",
  "city": "HongKong",
  "api_url": "http://<control-plane-host>:18080",
  "reboot_on_release": true,
  "reboot_delay_seconds": 3
}
```

## 3. v3.3 升级操作（Windows 节点）

下面以“服务模式（推荐用于池化）”为主；如果你们要快速验证抓屏问题，建议也走一遍“桌面手工启动”路径做对比。

### 3.1 升级前备份（强烈建议）

在节点机器上备份：
- `C:\ProgramData\SLC\node.json`
- `C:\ProgramData\SLC\logs\`（至少 `startup.log`、`config_load.log`、`slcsvc.log`）

### 3.2 停止服务（服务模式升级必做）

以管理员身份执行：

```bat
sc stop slcsvc
```

或打开 `services.msc`，找到 `SLC Node Service` 停止。

### 3.3 替换安装包文件

解压新的 `SLC-Pool-Node-GUI-v3.3.zip`，把以下文件覆盖到原安装目录（以你们实际目录为准）：

- `SLC.exe`（主程序）
- `SLCSvc.exe`（服务包装器）
- `service.bat`（服务安装/重配脚本）

注意：
- **不要覆盖/丢失** `C:\ProgramData\SLC\node.json`（配置在 ProgramData，不在安装目录）。

### 3.4 校验/更新 `node.json`

重点确认：
- `enabled=true`
- `device_id/device_secret` 与后端登记一致
- `api_url` 指向你们当前部署的控制平面（如 `http://8.210.183.180:18080`）

### 3.5 重新安装/重配并启动服务

管理员执行（安装包目录内）：

```bat
service.bat
```

它会执行：
- `sc create/config slcsvc ...`
- `net start slcsvc`

### 3.6 快速验证节点是否在线

1) 看服务是否运行：
- `services.msc` 中 `SLC Node Service` 为 Running

2) 看后端日志是否出现：
- `[NODE_CONN] _node_connected ... device_id=<你的 device_id>`
- `type=node_hello`、`type=node_heartbeat`

3) 看节点本地日志：
- `C:\ProgramData\SLC\logs\startup.log`（WS_DEBUG）
- `C:\ProgramData\SLC\logs\slcsvc.log`（确认 session）

## 4. 抓屏模式建议（对应你们“先走默认抓屏”的诉求）

你们控制端会在 `remoteSessionRequested.settings` 里携带 `streamMode`：

- `streamMode=0`：默认抓取真实桌面（不改显示器配置）
- `streamMode=1`：虚拟显示器独占（会创建虚拟屏并尝试设为主屏）
- `streamMode=2`：虚拟显示器扩展

建议策略：

1) **优先默认抓屏（streamMode=0）**  
适用：节点有真实屏幕（物理/HDMI dummy/云厂商提供显示输出）。

2) **当默认抓屏 `getSources count=0` 或抓屏崩溃时，再切虚拟显示器模式（1/2）**  
适用：节点是纯 headless GPU，系统没有任何可枚举的 screen source。

3) 虚拟显示器模式的前置：
- 需要你们依赖的虚拟显示器驱动（例如 Parsec VDD 或你们自带驱动方案）已正确安装。

## 5. 升级后验收清单（按日志对照最快定位）

### 5.1 后端侧应看到的顺序（关键）

1) `type=lease_assigned` 下发到 device
2) 节点回复 `type=lease_ready`
3) 用户发起远控：后端收到 `type=requestRemoteControlLease`
4) 后端转发：`type=remoteSessionRequested` 下发到 device
5) **节点应回：`type=offer`（最关键）**，后续还有 `candidate/answer`

若第 4 步后没有第 5 步：问题在节点侧“串流/抓屏/崩溃/未进入 startStreaming”。

### 5.2 节点回传远程日志的“卡点判断”

当你们启用了远程日志打点时（服务器上 `backend/logs/client_*.log`），按以下判断：

- 只看到：`准备调用 desktopCapturer.getSources`  
  - 更像：崩在 `getSources` native 内部（进程重启/服务重启）
- 看到：`getSources 成功, count=0`  
  - 更像：系统没有任何屏幕源（无显示器/虚拟显示器未生效）
- 看到：`准备调用 getDisplayMedia` 后不动  
  - 更像：创建流失败或权限/驱动问题
- 看到：`acceptRequest 已调用` 但后端仍无 offer  
  - 更像：信令发送链路异常（需看 NodeAgentService send(offer)/WS 状态）

## 6. 常见故障与处理（按优先级）

### 6.1 节点在抓屏阶段崩溃/重启（最常见）

表现：
- 远程日志停在 `desktopCapturer.getSources`
- 后端看到节点 WS 断线并重新连接（重新拉 token、拿到新的 connection_info）

处理建议：
1) 先确认节点是否在交互会话（非 Session 0）  
2) 确认系统存在可枚举显示器（物理/HDMI dummy/虚拟显示器）
3) 若是服务模式：短期用“桌面手工启动 SLC.exe（非服务）”对比验证  

### 6.2 节点断线重连导致 lease 无效

表现：
- 后端出现：`lease not found or not authorized`

处理：
- 这是预期保护：节点连接变化后旧 lease 不再可用。请**重新租赁**再远控。

### 6.3 NAT/防火墙导致 WebRTC 不通（有 offer 但黑屏/无法控制）

处理：
- 优先部署 TURN（coturn），并在客户端/控制端填入 TURN 配置。
